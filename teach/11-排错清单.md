# 11 · 排错清单

按"从编译到运行"的顺序排列，遇到问题从上往下对。

## 11.1 编译/链接阶段

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `Xtensa linker ... was not found in PATH`（这是 `build.rs` 特意给你的提示） | 没 source espup 的环境 | `source ~/export-esp.sh`；文件不存在就先 `espup install` |
| `linking with xtensa-esp32s3-elf-gcc failed` + 一段 `💡` 提示 | 缺符号/缺库/缺链接脚本；`build.rs` 的 `linker_be_nice` 会按符号名提示原因 | 按提示走：`linkall.x` 顺序、`esp-alloc` 的 `compat` feature、忘记初始化 `esp_rtos`/`esp-radio` 等 |
| `use of moved value: peripherals.GPIOx` | 外设句柄被 move 过了 | 别重复取；每个外设只能有一个持有者（第 03 课） |
| `future cannot be sent between threads safely` / spawn 报错 | 任务参数或跨 `.await` 持有的值不是 `Send`，而且你用的是 `SendSpawner` | 换成本地 `Spawner`，或改成"传所有权/用 AtomicX" |
| `panic_handler` 相关报错（duplicate / not found） | 每个二进制**只能有一个** `#[panic_handler]`，且必须有 | 新加的 bin 要自己写一个（照抄第 08 课） |
| `SpawnToken` 被 drop 的 panic（运行时） | 调了任务函数却没 `spawn` | `spawner.spawn(task().unwrap());` |
| `cannot find attribute main` / `no main` | 忘了 `#[esp_rtos::main]`，或 main 签名不对（必须 1 个 `Spawner` 参数、返回 `!`） | 对照第 08 课 |

## 11.2 烧录/连接阶段

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| `cargo run` 报找不到设备 | 调试器没插好 / 没权限 | `probe-rs list` 看是否枚举到；Linux 上装 udev 规则（probe-rs 文档给的 rules 文件） |
| `No such device` / 目标不匹配 | `--chip` 与板子不符 | 改 `.cargo/config.toml` 里 runner 的 `--chip=esp32s3` |
| `unwrap of \`scheduler.time_driver.as_mut()\` failed` | 忘了启动 esp-rtos 调度器，`Timer`/`Ticker` 没有时基 | 在 `boot::init()` 之后补 `let timg0 = TimerGroup::new(peripherals.TIMG0); esp_rtos::start(timg0.timer0, peripherals.FROM_CPU_INTR0);`（见 13 课） |
| 烧录报端口被占用 | 有别的进程占着探头（openocd、上一个没退出的 `cargo run`） | 关掉它们再试 |
| 烧进去了但**完全没有输出** | 只插了 USB 串口，没插调试器；或忘了 `rtt_init_print!()` | 项目用的是 probe-rs + RTT，必须接调试器；确认 main 第一行初始化了 RTT |

## 11.3 运行时阶段

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 打印一句 panic 后"死机" | 这是设计行为：`#![panic_handler]` 里 `loop {}` 停在原地，**不会重启** | 看 panic 信息定位；想要栈回溯就换 `esp-backtrace` |
| 看起来卡住、没有任何输出 | 可能卡在某个 `.await`（例如没拿到 IP 就 `wait_config_up`） | 打时间戳日志二分定位；给等待加 `with_timeout` |
| `Timer::after(...).await` 永远不返回 | 忘了 `esp_rtos::start(...)`（时基没起来） | 补上，且必须在第一个 `Timer` 之前 |
| Wi-Fi/BLE 初始化 `unwrap` panic，或分配失败 | 堆不够 | 调大 `heap_allocator!` 的两块大小（尤其 COEX 的 64 KiB） |
| `Unable to subscribe to events` | Wi-Fi 事件的订阅者数量不够（默认 2） | 在 `.cargo/esp-config.toml` 里设 `ESP_RADIO_CONFIG_EVENT_CHANNEL_SUBSCRIBERS = "4"`，然后 `cargo clean` |
| 栈溢出/玄学崩溃 | 局部大数组、递归、深调用链 | 看 `ESP_HAL_CONFIG_STACK_GUARD_*` / `ESP_HAL_CONFIG_ENSURE_MAIN_STACK_MINIMUM`；大缓冲改 static 或堆 |
| 改了配置没效果 | esp-config 是编译期读的，cargo 有 env 缓存 | `cargo clean` 后重建，并检查 `*_selected_config.md` 确认（第 07 课） |

## 11.4 加了新二进制之后

```bash
# Cargo.toml 里显式声明了 [[bin]] esp-s3；src/bin/ 下其它 .rs 会被自动发现为额外二进制
cargo run --bin led
cargo run --bin tasks
```

- 每个 bin 都要有自己的 `#![no_std] #![no_main]`、`#[panic_handler]`、`#[esp_rtos::main]`、
  `esp_app_desc!()`（照抄第 08 课最省事）。
- 不指定 `--bin` 时，cargo 会问你用哪个；runner（probe-rs）对所有 bin 都生效。

## 11.5 调试心法

1. **先让最小程序跑通**（第 08 课），再逐个加功能；每加一个功能就跑一次。
2. **能打印就能二分**：在怀疑的边界各打一条日志。
3. **怀疑硬件就换最简单的验证方式**（用 GPIO 输出+万用表/LED，而不是靠猜）。
4. **怀疑时序就用 `Instant::now()` 打点**；怀疑性能就 `--release` 对比。
5. **怀疑配置就看 `*_selected_config.md`**，别相信自己记忆里的默认值。
