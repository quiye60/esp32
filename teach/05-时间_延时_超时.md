# 05 · 时间、延时、超时

## 5.1 时基从哪来（复习）

```rust
let timg0 = TimerGroup::new(peripherals.TIMG0);
esp_rtos::start(timg0.timer0, peripherals.FROM_CPU_INTR0);
```

`embassy_time` 的 `Timer`/`Instant` 依赖"时间驱动"（time driver），这个驱动就是刚交出去的
`timg0.timer0`。所以：

- **没调用 `esp_rtos::start`** → `Timer::after(..).await` 不会正常完成，Wi-Fi 也起不来。
- `timg0.timer0` 被 move 走了，之后别再想用 `timg0.timer0`；`timg0.timer1` 还留着，可以自己拿去做别的。

## 5.2 四个最常用的 API

```rust
use embassy_time::{Duration, Instant, Ticker, Timer, with_timeout};

// 1) 睡一会儿（会 await，把 CPU 让出去）
Timer::after(Duration::from_millis(500)).await;

// 2) 打时间戳 / 测耗时（不阻塞，只是读时间）
let start = Instant::now();
// ...干活...
let elapsed_ms = start.elapsed().as_millis();   // u64

// 3) 周期任务：Ticker 会自动补偿处理时间，不会越跑越偏
let mut ticker = Ticker::every(Duration::from_millis(100));
loop {
    // ...周期工作...
    ticker.next().await;                        // 每 100 ms 醒一次
}

// 4) 给任何 future 加超时（比如等 Wi-Fi 连接最多 10 秒）
match with_timeout(Duration::from_secs(10), controller.connect_async()).await {
    Ok(Ok(info)) => rprintln!("connected: {:?}", info),
    Ok(Err(e))   => rprintln!("connect error: {:?}", e),
    Err(_)       => rprintln!("连接超时"),         // Err(TimeoutError)
}
```

> 注意：被 `with_timeout` 包住的 future 一旦超时就被丢弃。有的 future 不是"取消安全"的
> （丢在半路会留下半成品状态），用之前看一眼文档。比如 `connect_async` 超时后最好显式
> `disconnect_async()` 或重连。

## 5.3 `esp_hal::delay::Delay`：忙等，不是睡眠

```rust
use esp_hal::delay::Delay;

let delay = Delay::new();
delay.delay_millis(1);      // 内部实现是：while Instant::now() - start < 1ms {}，CPU 全速空转
```

也就是说 `Delay` 期间**CPU 什么都没法干**（不会被调度）。所以：

| 场景 | 用什么 |
| --- | --- |
| 等 LED 闪烁、等网络、等按键（毫秒~秒级） | `embassy_time::Timer` / `Ticker` |
| 驱动时序：给某个芯片几个微秒的建立时间 | `esp_hal::delay::Delay`（简单、精度够） |
| 想在同步代码里"睡一会儿"且不影响别的任务 | 没有好办法，改成 async，或交给 RTOS 线程 |

## 5.4 两个时间类型族别混用

| 来源 | 类型 | 用途 |
| --- | --- | --- |
| `embassy_time` | `Duration` / `Instant` / `Timer` | async 代码里的一切等待 |
| `esp_hal::time` | `Duration` / `Instant` | 驱动内部、同步/阻塞代码（`Delay` 就用它） |

它们**不是同一个类型**，不能互相传。看到 `expected embassy_time::Duration, found esp_hal::time::Duration`
这种错误，就是混用了。习惯上：业务层统一用 `embassy_time`，只在驱动/HAL 接口处转换。

## 5.5 时基精度与 RTOS tick

- `embassy_time` 的 tick 频率由 `embassy-time` 的 feature 决定（本项目是 `tick-hz-1_000_000`，即 1 µs 精度）。
- `esp-rtos` 的调度器 tick 是另一回事（由 `ESP_RTOS_CONFIG_*` 配置项控制，见第 07 课），
  影响的是**线程调度延迟**，跟你 `Timer::after(1ms)` 的精度不是一回事。
- 想要"精确到微秒级周期"，别靠软件循环——用外设（RMT / LEDC / 定时器 PWM），
  或者至少用 `Ticker` 而不是 `Timer::after`。
