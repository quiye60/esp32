# 06 · 日志与调试（RTT + probe-rs）

## 6.1 这个项目的日志链路

```rust
rtt_target::rtt_init_print!();   // main 里第一件事：初始化 RTT 打印通道（只能调一次）
rprintln!("Hello {}", 42);       // 之后的打印都走这里
```

- **RTT**（Real-Time Transfer）的做法是：芯片把输出写进 RAM 里的环形缓冲，调试器通过 JTAG
  后台把这块内存读走。所以对被调试的程序几乎零干扰。
- 前提是**插着调试器**并且用 `probe-rs`（`cargo run` 用的就是 `.cargo/config.toml` 里配的 runner）。
  只插 USB 串口 → 什么也看不到。
- 缓冲满的时候怎么办？rtt-target 的默认通道模式是 **`NoBlockSkip`：丢数据，但不阻塞程序**。
  这是有意的：没接调试器时程序也不会卡死。反过来说，**打印太快会丢**。

## 6.2 panic 为什么"看起来死机"

```rust
#[panic_handler]
fn panic(info: &core::panic::PanicInfo) -> ! {
    rprintln!("{}", info);   // 打印位置和消息
    loop {}                  // 停在这里，不重启、不退栈
}
```

- 只要有 RTT，你会看到一行 panic 信息（含文件:行号）。
- 看不到打印、硬件又像"卡住"了，先怀疑两种可能：**没有接调试器 / 程序真的在 panic 后死循环**。
- 想要栈回溯：把 panic 处理器换成 `esp-backtrace`（加依赖 + feature，能在 panic 时打印回溯），
  或者用 `defmt` 那套。现在这个模板给的是最简版，好处是直观。

## 6.3 defmt 和 log 是什么关系（以后可能用到）

| 方案 | 宏 | 过滤开关 | 说明 |
| --- | --- | --- | --- |
| 本项目现在 | `rprintln!` | 无 | 最简单，字符串在芯片侧就格式化好，代码大、速度慢一点 |
| `defmt` | `defmt::info!` | `DEFMT_LOG` | 只传索引+参数，主机侧格式化；省 flash、更快，但需要 `rtt_init_defmt!` / `defmt-rtt` |
| `log` + `esp-println` | `log::info!` | `ESP_LOG` | 生态通用；`esp_println::logger::init_logger_from_env()` 读环境变量 |

所以：**只有把日志前端换成 defmt/log，`DEFMT_LOG` / `ESP_LOG` 这些环境变量才有意义**。
现在这个项目只有一个 `rprintln!`，在 `.cargo/esp-config.toml` 里设 `DEFMT_LOG` 是没用的。

## 6.4 调试套路（比技巧更重要的是流程）

1. **先保证"能看见"**：烧进去点个灯 + `rprintln!`，确认输出和硬件动作都对（第 08 课）。
2. **二分定位**：在怀疑的地方前后各打一条日志，缩小到具体某一步。
3. **打时间戳**：`let t = Instant::now(); ... rprintln!("elapsed {} ms", t.elapsed().as_millis());`
   能直接告诉你"卡在哪、卡多久"。
4. **别在热路径狂打日志**：缓冲会丢、程序会变慢，反而掩盖问题。要高频观测就统计后定期汇总打印。
5. **善用配置项**：Wi-Fi 有 `ESP_RADIO_CONFIG_DUMP_PACKETS`，esp-hal 有一堆 `PLACE_*_IN_RAM`
   和性能相关开关（第 07 课）。真机调试时经常靠它们。

## 6.5 `cargo run` 之外的工具

```bash
probe-rs list                 # 调试器接上了吗
probe-rs info --chip esp32s3   # 目标芯片信息
cargo run                      # 编译 + 烧录 + RTT 输出
cargo run --release            # 怀疑性能/时序问题时用 release 复现
```

如果 probe-rs 报权限错误，通常是 udev 规则没装（见第 11 课）。
